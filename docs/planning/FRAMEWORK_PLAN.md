# Tiffany 后续实施计划

更新日期：2026-10-06。

本文只安排尚未完成的开发与验收工作。项目定位、核心约束与长期目标见 [target.md](target.md)；已实现能力和使用方式见 [README](../../README.md)、[源码地图](../CODE_MAP.md) 与 [学习路线](../LEARNING_GUIDE.md)。实际验证结果记录在 [部署验证记录](../DEPLOYMENT_VALIDATION.md)，不以“代码已写好”代替实机验收。

## 1. 贯穿后续开发的原则

**保留原始事件，按需读取字段，用 Hook 编写业务。**

```text
Adapter：处理协议与连接，只探测路由所需的元数据
Envelope：保留 raw 与来源、会话信息
Runtime / Scheduler：负责接纳、调度、监督和生命周期
Hook：表达业务行为，需要时才调用 Context.resolve(Field)
Provider：同步派生字段；I/O 放在 Hook 或 Service
Client：执行平台动作
```

新增能力先判断能否通过 Hook、Provider、Service 和 Scope 组合完成。只有涉及平台无关的运行机制时才修改 `core/`。配置组装留在应用层，安装和进程监督留在部署层；不在事件入口构造完整的平台对象，也不因新增诊断而预取字段。

下面的阶段按依赖关系推进，不预设发布日期。每个阶段完成后，将对应事项移出本文，并把交付说明写入使用文档、验证结果写入验证记录。

| 阶段 | 待完成内容 | 对应目标 | 进入下一阶段的条件 |

## 3. P0：完成首个服务器版本的实机验收

当前尚缺真实平台与 Linux 长时间运行的证据。此阶段完善验收与必要修复，不重复开发已有启动器、路径存储、扫码、日志或健康接口。

### 待办

- 确认包含 Windows 短路径、旧编码修复的新提交在现有 Linux/Windows CI 矩阵中通过。
- 在 Windows 终端实际验证首次 Ctrl+C、再次 Ctrl+C、启动中取消及退出后的进程残留。
- 在 Linux 上通过 `screen` 从其他工作目录启动，检查凭据及备份权限、停止信号和实际 45 秒停止上限。
- 使用真实 NapCat 验证消息回复、断线重连、过载时响应帧仍能处理，以及停止期间已接纳事件的回复。
- 使用真实 QQ 官 Bot 验证扫码、凭据复用、群与 C2C 私聊、权限失败提示、断线恢复及停止行为。
- 实机执行一次覆盖更新与旧版本回滚，逐字节比较配置、凭据和业务文件，检查历史日志保留。
- 完成至少 24 小时持续运行，记录版本、环境、消息负载、资源使用、重连和退出结果。

### 验收

把操作步骤、脱敏结果、发现的问题及修复后的复测写入 [部署验证记录](../DEPLOYMENT_VALIDATION.md)。发布前不留阻断启动、数据保留或正常停止的问题；尚未取得的真实平台结果明确标为未验证。

## 4. P1：用配置组合扩展

目前应用通过 [hooks/__init__.py](../../hooks/__init__.py) 固定注册业务。下一步让用户在配置中选择功能，同时保留直接写一个 Hook 的入口。

### 实现范围

1. 在应用层建立显式扩展注册表，以稳定 ID 定位扩展；先支持随项目提供或由应用明确注册的本地扩展。
2. 在 TOML 中声明启用项与各自配置。先用单层配置，普通启动只读，不自动改写已有文件。
3. 每个扩展取得独立 Scope，通过 Scope 注册 Hook、Provider、Service 和生命周期资源。调整现有业务注册函数，使其可以由组合入口安装；复用原有业务逻辑。
4. 分开处理配置校验、依赖排序、注册和启动。服务依赖使用同一 ServiceKey，Field 使用共享实例；稳定扩展 ID 不改变字段与服务键的身份语义。
5. 安装失败时撤销本次已安装项。撤销受阻时保留资源并报告原因，不继续启动半完成的应用。
6. 提供只读的组合说明，列出最终启用项、来源、配置摘要、所属 Scope 及声明依赖；敏感配置脱敏。

配置节名和注册函数签名在实现前确定；本文不把设想中的接口当作现有 API。扩展加载器放在应用组合层，`core/` 继续只提供运行机制。

### 验收

- 配置启用或停用 `ping` 无需修改 `application.py`；不启用命令扩展时不注册其派生字段。
- 未知或重复 ID、配置类型错误、依赖缺失或循环在连接平台前说明原因。
- 同一配置产生确定的组装结果；扩展之间共用服务时归属唯一。
- 第二个扩展安装失败时，第一个扩展的注册与资源能够回滚；取消未收敛时给出失败报告。
- 新进程中单独使用 `Bot()` 不触发扩展扫描、配置读取、目录创建或可选依赖导入。

## 5. P2：证明业务可组合，接入可扩展

### 5.1 可选业务扩展

先提供权限与限流两个独立示例，使用 P1 的同一注册方式，默认不启用。

| 扩展 | 最小职责 | 落点 |
| --- | --- | --- |
| 权限 | 按显式配置的用户/会话规则允许或拒绝后续业务；明确判断顺序与默认规则 | Hook + 共享 Field；需要异步查询时调用 Service |
| 限流 | 按会话或用户限制业务频率，限制状态数量并清理过期状态 | Hook + Scope 拥有的 Service |
| 持久化示例 | 演示异步保存业务状态、格式版本和恢复错误处理 | 可运行示例 + `APP_PATHS.storage` + 可替换 Service |

业务限流与 Scheduler 的资源容量分开配置。持久化示例只保存业务状态，不把事件队列改为持久队列，也不把数据库依赖加入基础核心。

**验收：**相同业务在 OneBot 与 QQ 官 Bot 上使用共享字段运行；停用扩展后不执行相应判断、不保留其后台资源。权限拒绝的事件不进入后续业务 Hook；限流状态有明确容量与过期策略；持久化示例通过覆盖更新、重启恢复及损坏文件场景，并提供完整学习步骤。

### 5.2 可复用的 Adapter 契约

基于现有协议测试提炼供新 Adapter 复用的契约测试，不重写已具备的连接与生命周期机制。

- 说明路由类型、会话键、连接就绪、回复能力及不支持场景的含义；控制帧和鉴权由接入层处理。
- 整理最小事件夹具，验证 `raw` 保留、字段按需解析、共享字段的缺失语义，以及 Provider 注册和撤销。
- 验证过载、断线、重连、启动失败与关闭的共同约束，同时保留各协议不同的确认、去重和丢弃策略。
- 提供自定义事件源的完整示例，说明怎样复用契约测试，并通过现有 Bot 与 Client 接口接入业务。

**验收：**现有 OneBot、QQ 官 Bot 和示例事件源能运行适用的同一组契约；未被 Hook 读取的业务字段不解析。平台独有能力仍通过 `raw`、自定义 Field 或 Client 暴露，不扩充成必须全量构造的统一消息模型。

## 6. P3：让组合、执行和开销可以解释

复用现有注册来源、Trace、指标和微基准，补齐面向扩展开发者的查看入口与回归方法。

### 待办

- 从公开的只读视图说明 Hook 顺序、过滤条件、Field/Service 依赖与资源归属，避免诊断工具依赖 Runtime 的私有集合。
- 让启动诊断把配置启用项与实际注册结果对应起来；查看结果不连接平台、不执行 Provider、不展示凭据。
- 在显式启用时，用现有 Trace 解释一次事件为何命中、跳过、停止或失败，记录范围与采样仍有界，默认关闭。
- 为扩展数量、会话积压、慢 Hook 和诊断开关建立可复测的开销基线；性能结论同时说明输入、环境与统计方法。
- 为 P1/P2 的完整扩展示例同步补充源码导航、可执行示例和依赖说明。

### 验收

使用者能从启用配置追踪到注册来源和执行结果。默认诊断不会保存原始消息、主动解析字段或增加网络 I/O。性能回归先在相同环境重复测量并分析原因，再决定是否阻断发布，不把现有本机微基准数值当作跨机器的固定门槛。

## 7. 有需求后再启动的方向

以下是未来展望，尚未进入交付阶段。启动其中任一项前，需补充最小范围、协议或生命周期边界与验收方案。

| 方向 | 启动条件 | 保持核心思想的做法 |
| --- | --- | --- |
| QQ Webhook 或其他接入协议 | 现有接入无法满足实际部署需求，且能提供真实联调环境 | 新增 Adapter，复用 Provider 与 Client；在接入层定义鉴权、确认、重试和过载语义 |
| 多账号、多 Adapter 组合 | 单账号限制实际业务，且明确账号隔离与回复归属 | 应用层组装独立接入；凭据、连接、会话键和就绪状态分别归属账号 |
| 开发用事件录制与离线重放 | 真实问题难以用手工夹具复现 | 显式启用、脱敏、有保留上限；使用假 Client 避免重放向真实平台发送消息 |
| 扩展热替换 | 停机更新无法满足实际需要 | 先定义在途事件、共享依赖和失败恢复语义，再设计新旧 Scope 的切换 |
| 跨重启恢复事件处理 | 产品明确需要补发或审计，并接受存储与迁移成本 | 先定义投递、幂等和恢复语义；不对平台与外部副作用承诺恰好一次 |
| AI、群管等复杂业务 | 有具体使用场景与可验证的接口需求 | 独立 Hook/Service 扩展，依赖按需安装，继续使用相同注册与清理路径 |

插件市场、Web 管理后台、大型配置叠加系统和完整平台 API 全量封装当前不列入实施队列。

## 8. 每次交付的检查

- 是否解决了明确的问题，且职责仍属于正确层？
- 是否保留 raw、懒解析和同步 Provider，且未用 `needs` 预取字段？
- 注册、在途任务与清理是否有明确 owner，失败能否回滚或报告？
- 是否维持有界队列、会话内 FIFO 与跨会话公平性，且没有扩大投递承诺？
- 是否说明新增配置的默认值、兼容性与数据保留方式？
- 是否补充适合该改动的行为验证，并更新使用、学习与源码导航？

完成后从计划删除对应待办；只实现但尚未实机验收的事项移为验收任务，不继续列成待开发功能。
