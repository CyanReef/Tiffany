# Tiffany 方向与目标

更新日期：2026-10-06。

本文定义 Tiffany 后续发展的方向、必须保持的核心约束，以及尚未完成的目标。具体实施顺序见 [FRAMEWORK_PLAN.md](FRAMEWORK_PLAN.md)；现有功能和 API 以 [README](../../README.md)、[源码地图](../CODE_MAP.md) 与 [学习路线](../LEARNING_GUIDE.md) 为准。

## 1. 项目定位

**保留原始事件，按需读取字段，用 Hook 编写业务。**

Tiffany 的长期方向是一个轻量、可组合、生命周期明确的异步 Hook Runtime。开发者可以从一个异步函数开始，需要数据时使用 Field，需要共享能力时使用 Service，需要整体管理扩展时使用 Scope。

核心提供平台无关的运行机制。行为由 Hook 承载，数据由同步 Provider 按需派生，平台接入与动作由 Adapter、Client 完成。功能变多时，这条调用关系仍应清晰可读。

```text
Adapter 接收并最小探测
  → Envelope 保留原始事件
  → Runtime / Scheduler 接纳和调度
  → Hook 执行业务
      → Context.resolve(Field)：需要时才调用同步 Provider
      → Service：调用显式声明的共享能力
      → Client：异步回复或执行平台动作
```

协议解码、控制帧处理和路由元数据探测属于接入所需的工作；业务字段继续按需计算。未来增加协议时，保留平台特有能力与原始数据入口，不要求先转换成完整的统一消息对象。

## 2. 必须保持的核心约束

| 约束 | 对后续开发的要求 |
| --- | --- |
| 原始事件保留 | 路由与派生字段不覆盖 `raw`；平台特有数据始终可访问 |
| 字段按需计算 | `needs` 声明依赖并用于校验，不预取字段；同一事件共享解析缓存 |
| Provider 同步派生 | 只进行同步、确定性的字段计算；网络、数据库与文件 I/O 放在 Hook 或 Service，阻塞操作不占用事件循环 |
| 业务使用同一扩展机制 | 命令、权限、限流、AI 等通过 Hook/Provider/Service 组合；随项目提供的业务扩展没有特殊执行路径 |
| 核心与平台、部署分离 | `core/` 不导入具体协议、业务扩展或部署入口；独立使用核心不要求登录账号或生成运行配置 |
| 依赖与身份明确 | 共用同一个 Field/ServiceKey 实例；名称用于诊断，扩展 ID 用于组装，不代替键的身份 |
| 注册时确定资源归属 | 一个资源由一个 owner 管理；共享服务通过声明依赖使用，卸载消费者不清理提供者的资源 |
| 清理结果真实可见 | 停止、取消和卸载说明在途工作与剩余资源；无法收敛时保留必要资源并报告失败 |
| 工作与状态有界 | 维持队列、并发与缓存上限；同一会话 FIFO、不同会话公平调度，不承诺整个连接的全局 FIFO |
| 可选能力按需启用 | 未启用的业务扩展与诊断不执行工作；新增可选依赖不强制进入基础核心 |

当前事件队列与去重缓存使用内存。业务持久数据可以由 Service 保存；后续若增加事件恢复，必须另行定义投递与幂等语义，不把“持久化”直接解释为跨进程恰好一次处理。

### 职责应落在哪里

| 层 | 负责的变化 |
| --- | --- |
| `core/` | 平台无关的路由、字段解析机制、调度、监督与生命周期 |
| `adapters/`、`clients/` | 协议连接、鉴权、最小探测、平台字段和外部动作 |
| `hooks/` 或独立业务扩展 | 业务判断、派生字段、权限、限流及功能组合 |
| 应用组合层 | 选择扩展与接入、读取应用配置、安装依赖关系、提供健康状态 |
| `deployment/` | 环境准备、首次配置、凭据存储、进程监督与发布操作 |
| `shared/` | 无业务含义且只依赖标准库的跨层约定 |

保持现有公开入口可理解；内部目录按职责拆分。新增模块前说明其职责与调用方向，避免为了扩展而引入一套平行的事件、解析或生命周期系统。

## 3. 下一阶段的目标

下列目标尚未完成。它们描述要达到的结果；实现任务、优先级和验收步骤由 [实施计划](FRAMEWORK_PLAN.md#2-优先级与交付顺序) 管理。

### G1：服务器运行取得真实证据

首个可部署版本要在真实 Linux 服务器、NapCat 与 QQ 官 Bot 上完成收发、恢复、停止、覆盖更新和回滚验证，并完成至少 24 小时持续运行。Windows 测试入口的交互停止也要取得实测结果。

**成功标准：**当前修复后的 CI 矩阵通过，实机记录能复现操作与结果；数据保护、凭据权限和停止上限得到验证。真实平台尚未验证的能力明确列出，自动化假服务测试与真实平台验收分别记录。

### G2：功能组合由配置表达

使用者能通过配置选择本地扩展，并理解实际启用了哪些功能。开发者既能直接注册一个 Hook，也能把一组 Hook、Provider、Service 封装为独立扩展。

**成功标准：**启停功能无需改应用入口；稳定 ID、独立 Scope 与依赖校验共同确定组装结果；安装失败能回滚或准确报告残留。扩展加载与配置逻辑留在应用层。

### G3：新接入遵循可验证的最小契约

让新增 Adapter 有明确的接入说明和可复用的契约测试，覆盖 raw、会话键、共享字段、连接状态、回复与资源撤销。共同契约之外的协议差异保留在接入实现和文档中。

**成功标准：**现有两种接入与一个示例事件源通过适用的同一套契约。增加平台不要求新增核心平台分支，也不迫使无关 Hook 解析该平台的完整事件模型。

### G4：用可选扩展证明核心足够通用

提供权限、限流与业务持久化的完整示例，展示复杂行为如何通过现有机制组合，而不是逐项加入核心。示例默认不启用，开发者按需要安装和配置。

**成功标准：**权限与限流共享相同业务字段并能组合运行；持久化示例有版本与错误处理。启用、停用、安装失败和资源清理均可验证，学习文档覆盖从安装到追踪执行的全过程。

### G5：增加功能后仍可阅读、诊断和复测

开发者能回答“这个功能由谁安装、依赖什么、为什么执行或跳过、卸载后还剩什么”。诊断复用现有 Trace、指标与来源记录；性能评价依据相同环境下可复测的数据。

**成功标准：**配置与注册的只读说明能对应到源码和执行记录，不暴露凭据、不主动解析字段。新扩展具有可运行示例和清晰导航；慢 Hook、多会话与诊断开销有明确测试方法，API 变化附迁移说明。

## 4. 长期展望与启动条件

长期可以发展更多协议、多账号组合、离线录制与重放、扩展热替换及跨重启恢复。这些方向只在真实需求出现、最小范围和验收语义确定后进入实施；具体条件见 [计划中的未来方向](FRAMEWORK_PLAN.md#7-有需求后再启动的方向)。

AI 对话、群管和其他产品能力沿用普通扩展路径。插件市场、Web 管理后台、复杂配置叠加和平台 API 全量封装当前没有排期。

新方向应回答三个问题：解决谁的具体问题；能否在现有职责层完成；如何证明它没有破坏原始事件、懒解析与资源归属。若答案不清楚，先以独立示例验证，再决定是否纳入框架。

## 5. 目标与计划的维护

- `target.md` 保存项目方向、核心约束和未完成目标；`FRAMEWORK_PLAN.md` 保存实现顺序、任务范围与验收条件。
- 已交付的功能从计划待办中移除，使用方式写入 README、学习文档或协议文档；历史演进由提交记录保留。
- 代码实现与实机验收分别记录；前者完成而后者缺失时，只保留验收任务。
- 目标达成后从未完成目标中移除；新增目标应说明问题、职责层和成功标准。
- 每轮开发后同步检查文档与实际能力，避免路线图继续出现已经完成的基础功能或失效的目录草图。
